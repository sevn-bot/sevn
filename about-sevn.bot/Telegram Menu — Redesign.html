Telegram /config menu — proposed redesign (shipped 2026-07-27)

Live source of truth: about-sevn.bot/Telegram Menu.html — CI-gated by make telegram-menu-docs-check. This file is a historical design artefact for the 19→8 tile regroup; the running bot matches the live catalog.

A structural proposal that shipped on branch wave/telegram-menu-redesign. Status data re-verified against 519b0321 at authoring time.

Problem. The root keyboard is 19 tiles deep — a 10-row wall of buttons where Session, Notifications, Shortcuts, Channels and Voice are five separate destinations for one idea ("how the chat behaves"), Advanced is a dumping ground for five unrelated sub-sections plus two orphan toggles, and sevn.bot sits next to My sevn bot with no way to tell them apart. Meanwhile only 20 of the 126 sevn CLI leaf commands have a menu destination that works today — see the coverage tab.

Proposal. Eight root tiles grouped by what the operator is trying to do, every section under 14 rows, no leaf deeper than three taps, and full sevn CLI coverage.

Five diagnoses

  • One idea, five doors. Session, Channels, Notifications, Shortcuts and Voice all answer "how does this chat behave?" — they are now one 💬 Chat tile.
  • Advanced was a junk drawer. It held RLM, Self-Improve, Second Brain, Sub-agents and CodeMode — five unrelated things whose only shared trait was "we had nowhere to put it" — plus two orphan toggles (auto-resume, trace redaction) that belonged to Deployment and Health. Advanced is dissolved; every child gets a real home.
  • Two tiles named the same thing. sevn.bot (upstream project: sync, bugs, features) vs 🤖 My sevn bot (this install: restarts, tunnel, ids). Now: the project lives under ❓ Help, the install under 🖥 Deployment.
  • Near-empty tiles cost a full row. Tools (0 action rows), Secrets (1), Shortcuts (1), Notifications (1), Agents (1), Integrations (1) each burned a root slot for one button. They are now rows or sub-sections.
  • Duplicated controls drift. "Trace redaction" existed on both Advanced and Logs — and the two copies do not even have the same status: the Logs one is live, the Advanced one is gated. "Queue mode" was on both Session and Sub-agents. Each control now has exactly one home.

Five rules the new tree follows

  • Group by operator intent, not by config file shape. Root tiles answer questions an operator actually asks ("is it healthy?", "who can talk to it?"), not sevn.json top-level keys.
  • ≤ 8 root tiles, ≤ 14 rows per screen. Four thumb-reachable rows at root; no screen needs a long scroll on a phone.
  • ≤ 3 taps to any leaf. Root → section → sub-section. Nothing goes deeper except the two pre-existing setup flows (Discogs setup, Sub-agents running list).
  • One home, many cross-links. Every control is owned by exactly one section; other sections may link to it (e.g. Chat › Channels links to Access › DM policy) but never duplicate it. This is why the persistent-tunnel switch is not repeated inside Tunnel setup.
  • Frequency wins the top row, and working buttons never get demoted. Model pickers, queue mode, restarts, the tunnel switch, tail logs and "add secret" stay on their section's first screen; rare and destructive things sink into sub-sections behind a confirm.

The eight tiles, and why each earns a root slot

  • 💬 Chat — the surface the operator is literally standing in. Highest-frequency tweaks (queue mode, quick actions, notifications).
  • 🧠 Agent — "who answers and with what model". Second-highest frequency: model switching.
  • 🧩 Skills & Tools — what sevn can do. Grows fastest as skills ship, so it needs its own room.
  • 📚 Memory — what sevn knows: Second Brain, Dreaming, code understanding, OpenWiki.
  • 🔐 Access — credentials in, and the guard rails on content coming in. Security-sensitive things read better together.
  • 📊 Health — is it working, what did it cost, what happened. The on-call tile.
  • 🖥 Deployment — my install: services, the public tunnel, config file, versions, upgrades. The tile with the most live owner actions.
  • ❓ Help — commands, guides, and the sevn.bot project itself (sync / bugs / features).

How CLI parity is achieved without bloating the menu

  • Section captions are sevn config <section>. Every section already renders live state in its caption bubble; formalising that as "the caption is the section's config dump" covers 20 of the 21 sevn config <section> commands with zero extra buttons.
  • Read-only commands become one action row that posts its output as a message (doctor, usage show, skills list, tools health, secrets list, sessions list, tunnel status).
  • Commands taking free-form input become forms (config set, memory search, sessions history, message send, subagents kill, turn-bundle view, tunnel setup).
  • Host-shell-only commands get a copy-paste card, not a fake button. completion install, shell-history install, secrets store-passphrase, onboard, gateway set-gateway-token, dashboard set-login-password and unboard mutate the operator's own shell/Keychain — 🖥 Deployment › Host-only commands prints the exact command instead of pretending Telegram can run it.
  • Repo-only commands are quarantined. readme *, about-docs * and gui migrate only make sense inside a source checkout; they live under ❓ Help › Developer, owner-gated and hidden when no checkout is bound.

Where the status data comes from

Read from code (not hand-guessed)

  • live and gated are computed from the running gateway: every keyboard was rendered via build_config_menu_keyboard() and each callback resolved through menu_readiness.readiness_for_callback() and menu_registry.match_menu_button_spec().
  • Result across the current menu: 24 WIP rows and every matched spec with implemented=True — so nothing in the live menu is a dead handler. The 24 WIP rows are gated purely by the _READY_SPEC_IDS allow-list in menu_readiness.py, which is why unblocking one is a one-line change plus a functional check.
  • Spec ids (C1.6, C20.4, C22.1, …) shown on each row are the real MenuButtonSpec.spec_id values, so you can grep them straight into menu_registry.py.
  • Re-verified at 519b0321 after the tunnel work merged (PR #58). Diff against the earlier snapshot: exactly one row added (C22.1, Ready), nothing removed, no readiness changes. All 88 spec assertions in this document still match the live menu.

Classified by hand (my judgement, verify before planning)

  • wire-up means I found an existing callable in this repo that already does the work — a CLI command, a gateway module, or a store API. Spot-checks behind the calls: PairingStore.list_pending()/approve_code(), shortcuts_store.delete_shortcut()/list_visible_shortcuts(), list_guide_topics(), the /new and /stop CommandSpec rows in commands/registry.py.
  • build means I did not find a callable path from the gateway process: the copy-paste card renderer, the repo-checkout guard for developer rows, the destructive-export flow, and the integrations status listing.
  • The wire-up/build split is an estimate of shape, not effort. Treat it as a starting point for a wave plan, not as sizing.

Two patterns the tunnel work established — reuse them

Two-step confirm

  • act:tunnel:on matches ^act:tunnel:on(:confirm|:cancel)?$ and renders through build_tunnel_on_confirm_keyboard() + tunnel_on_confirm_message(). Turning off takes no prompt — it only reduces exposure.
  • That asymmetry is the right rule and should be copied verbatim by the other irreversible/exposure-increasing rows in this plan: secrets rm, export-secrets, unboard, and deploy remote.
  • It is a better precedent than the Discogs setup flow, which is a linear wizard rather than a guard.
  • 2e4ea761 also set the error-handling rule: unknown tunnel:* callbacks are rejected, not silently treated as "stop". New callback families should reject unknown suffixes the same way rather than falling through to a default action.

Conditional rows

  • _tunnel_toggle_row() returns None unless infrastructure.tunnel.mode is in RUNNABLE_MODES — the row simply is not rendered when no provider is configured.
  • This is cleaner than a 🚧 row for capability-gated controls, and the same treatment suits Memory › OpenWiki (hide until installed), Help › Developer (hide without a checkout) and per-skill sub-sections.
  • But it leaves a gap. With mode: none, an operator sees nothing about tunnels at all and has no path to configure one from Telegram. The 🌍 Tunnel setup sub-section in this plan exists specifically to close that: it is always present, and sevn tunnel setup becomes reachable.

What has to change in code

Touch points

  • src/sevn/gateway/menu/menu.py — _CONFIG_ROOT_TILES (19 → 8), _CONFIG_SECTIONS (27 → 43 ids), and one _build_<section>_keyboard_rows per new section. _build_my_sevn_bot_keyboard_rows() becomes the Deployment builder and keeps _tunnel_toggle_row() unchanged.
  • src/sevn/gateway/menu/menu_registry.py — MenuButtonSpec rows keyed by callback data; renamed sections change cfg:section:* ids, so specs move with them. act:* rows (restarts, tunnel, sevn.bot) keep their callbacks and need no change.
  • src/sevn/gateway/menu/menu_readiness.py — _READY_SPEC_IDS allow-list; already-Ready callbacks keep their ids where the callback string is unchanged. Its section blurbs mention "My sevn bot" and need re-pointing at Deployment.
  • src/sevn/cli/config_sections/ — sevn config <section> subcommands are 1:1 with section ids; adding/renaming sections regenerates this surface (sevn config sections is the SSOT listing).
  • scripts/telegram_menu_catalog.py + scripts/check_telegram_menu_docs.py — the docs gate parses Telegram Menu.html; it must be re-scaffolded (make telegram-menu-docs-scaffold) once the new keyboards land.
  • scripts/check_cli_help_docs.py — unchanged, but ROOT_COMMAND_PANELS panel names ("Ops", "Core", "Surfaces", …) should be re-pointed at the eight menu groups so CLI help and Telegram tell the same story.

Sequencing (safe, gate-by-gate)

  • 1. Callback-stable move. Re-parent existing sections under the 8 new tiles without renaming any cfg:* or act:* callback data. Nothing in menu_readiness or the registry changes; only _CONFIG_ROOT_TILES and the nav rows do. Ships the root-level win on its own, and every live row — the tunnel switch included — stays exactly as live as it is now.
  • 2. Clear the gated backlog. 24 rows are implemented but not allow-listed. Verify each and add its spec id to _READY_SPEC_IDS — the cheapest operator-visible win available, and independent of the restructure. Switch the filter above to "Works + 1-line unblock" to see exactly what it buys.
  • 3. Dissolve Advanced. Move its two orphan toggles (gateway.restart.auto_resume_b → Deployment, tracing.redaction.enabled → Health › Trace export, de-duplicating the Logs copy) and delete the section id.
  • 4. Rename section ids (session→chat, my_sevn_bot→deployment, …) behind an alias table so old callback payloads in already-sent messages still resolve. Regenerate sevn config subcommands.
  • 5. Add the new leaves — the wire-up and build rows. Tunnel setup is a good first one: four rows, one existing CLI surface, and it closes the mode: none dead end. Add ids to _READY_SPEC_IDS as they land so unfinished rows stay 🚧-prefixed rather than silently dead.
  • 6. Re-scaffold docs — make telegram-menu-docs-scaffold, then make ci-docs.

Open decisions

  • Persistent vs one-shot tunnel control. act:tunnel:on/off sets autostart and survives reboots; sevn tunnel start/stop is this-boot-only process control. Two controls, near-identical names. This plan keeps the switch on the Deployment screen and relabels the CLI-backed pair to "Start now / Stop now" inside Tunnel setup. If you would rather not surface the one-shot pair at all, drop those two rows — the plan loses two CLI leaves and nothing else.
  • Owner gating. Access, Deployment and Help › Developer are owner-only — _build_my_sevn_bot_keyboard_rows(is_owner=…) already does this for the tunnel and restart rows. Non-owner paired users should see a 4-tile root (Chat, Agent, Skills & Tools, Help). Needs a per-tile owner_only flag on the root tile tuple.
  • Dynamic sub-sections. Skills & Tools currently hard-codes Social Media Manager and Discogs. As skills ship, this should page over the skills inventory rather than grow a row per skill.
  • Long output. doctor, config show and skills list exceed Telegram's 4096-char message limit; they need the existing paginated/file-link path rather than a raw dump.

Deliberately not executable from the menu

  • All 126 leaves have a destination — but 9 of them (completion *, shell-history *, onboard, secrets store-passphrase, gateway set-gateway-token, dashboard set-login-password, unboard/uninstall/remove) appear as copy-paste instructions, not executable buttons, because they act on the operator's own machine outside the gateway's reach.
  • 11 more (readme *, about-docs *, gui migrate) are shown only when a source checkout is bound.
  • If you would rather these be hidden entirely, the change is one flag on Help › Developer and Deployment › Host-only commands — the rest of the tree is unaffected.
